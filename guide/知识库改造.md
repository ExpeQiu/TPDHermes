我基于当前项目的 KB 架构直接整理一版可落地的导入方案，重点对齐现有 `Chroma -> kb_cache -> /knowledge` 这条链路，避免设计成和现状脱节的空方案。

**设计定位**
- 这版方案对齐当前项目的现状：外部 Chroma 作为主知识库，本地 `kb_cache` 作为镜像与降级展示层，`/knowledge` 页面消费 cache 中的目录树与详情。[kb_proxy.py](file:///Volumes/Lexar/git/03T/TPDHermes/backend/services/kb_proxy.py) [kb_cache.py](file:///Volumes/Lexar/git/03T/TPDHermes/backend/services/kb_cache.py) [kb_browse.py](file:///Volumes/Lexar/git/03T/TPDHermes/backend/services/kb_browse.py) [page.tsx](file:///Volumes/Lexar/git/03T/TPDHermes/src/app/knowledge/page.tsx) [kb.py](file:///Volumes/Lexar/git/03T/TPDHermes/backend/routes/kb.py)
- 目标不是“直接往 `kb_cache` 塞数据”，而是形成一条正式链路：`原始文档 -> 解析/切分 -> 写 Chroma -> 同步 kb_cache -> /knowledge 治理与验证`。
- 设计原则是 4 个词：`可治理`、`可追踪`、`可重入`、`可发布`。

**Collection 规范**
- 命名格式建议统一为：`<scope>.<domain>.<topic>.<lang?>`
- 推荐全部使用小写英文、点分隔，避免空格、中文、斜杠。
- `scope` 建议固定枚举：`public`、`internal`、`project`
- `domain` 对齐知识域，不对齐项目名；建议复用 `metadata.domain`
- `topic` 表示主题簇，不要过细到单篇文档
- `lang` 可选，只有多语言场景再加，比如 `zh`、`en`

**命名示例**
- `public.structured_tech.autonomous_driving`
- `public.public_intel.competitor_news`
- `public.release_assets.vehicle_launch`
- `internal.ops.process_docs`
- `project.ev_sedan.pitch_materials`

**命名约束**
- 一个 collection 对应一类“长期可复用知识池”，不是一次性上传批次
- 不建议以日期命名 collection，例如 `2026_05_docs`
- 不建议以单篇文档命名 collection，例如 `tesla_report_md`
- 一个 collection 的 chunk metadata 结构必须一致
- 业务侧展示时可额外维护别名 `display_name`，但存储层仍使用规范名

**Domain 规范**
- `metadata.domain` 建议固定枚举，优先作为 `/knowledge` 树根
- 初始建议值：
  - `public_intel`
  - `structured_tech`
  - `release_assets`
  - `market_research`
  - `policy_regulation`
  - `internal_methodology`

**Metadata 模板**
- 现有页面和目录树已经依赖这些字段：`title`、`domain`、`folder_path`、`tags`、`source_url`、`published`、`linked_kg_ids`。[产品1.2升级方案.md](file:///Volumes/Lexar/git/03T/TPDHermes/guide/%E4%BA%A7%E5%93%811.2%E5%8D%87%E7%BA%A7%E6%96%B9%E6%A1%88.md#L192-L205)
- 建议把 metadata 分成 3 层：检索层、治理层、追踪层。

**字段约束**
- 必填字段：
  - `id`
  - `title`
  - `domain`
  - `folder_path`
  - `source`
  - `published`
  - `doc_id`
  - `chunk_index`
  - `chunk_count`
- 强烈建议字段：
  - `tags`
  - `source_url`
  - `language`
  - `checksum`
  - `ingest_job_id`
  - `updated_at`
- 可选字段：
  - `linked_kg_ids`
  - `projects` 或 `project_ids`
  - `authors`
  - `source_type`

**字段语义**
- `id`：chunk 级唯一 ID，写入 Chroma 主键
- `doc_id`：文档级唯一 ID，用于重建和整体覆盖更新
- `folder_path`：决定 `/knowledge` 的目录树位置
- `published`：决定是否可进入执行侧知识范围
- `linked_kg_ids`：与图谱联动锚点
- `checksum`：判断文档是否变化，支持幂等更新
- `ingest_job_id`：定位这次导入任务，便于回滚和审计

**最小 Metadata 模板**
- 如果你想先快速上第一版，最少至少写成这样：

```json
  "source": "manual_import",
  "source_url": "https://example.com/doc001",
  "published": true,
  "chunk_index": 1,
  "chunk_count": 5

```

**导入脚本输入格式**
- 推荐支持两种输入模式：`manifest 模式` 和 `目录扫描模式`
- 第一版优先做 `manifest 模式`，更稳定、可控、易重跑

**建议 CLI 形式**
- 推荐脚本命令：

```bash
python3 scripts/kb_ingest.py \
  --manifest /data/imports/autodrive_manifest.json \
  --collection public.structured_tech.autonomous_driving \
  --chroma-url http://localhost:8001 \
  --sync-cache \
  --project-id __all__
```

**脚本内部处理流程**
- 读取 manifest 或扫描目录
- 解析文件，统一转成 Markdown/纯文本
- 清洗内容，去掉导航、版权噪声、空白段
- 按标题或长度切 chunk
- 为每个 chunk 生成 `id` 和 metadata
- 写入 Chroma collection
- 成功后调用现有 `/api/v1/kb/cache/sync`
- 输出结构化结果 JSON

**脚本失败策略**
- 单文档失败不影响整批，最终汇总错误
- 支持 `--dry-run`
- 支持 `--replace-doc-id <doc_id>` 全量重建单文档
- 支持 `--skip-if-checksum-same`
- 支持 `--delete-missing-chunks`，用于覆盖更新

**新增 API 草案**
- 第一阶段建议新增 4 个 API，先把上传和导入打通，不急着做复杂工作流。

**1. 上传原始文件**
- `POST /api/v1/kb/upload`
- 作用：接收原始文件，保存到临时区，返回文件引用
- 请求：`multipart/form-data`
- 字段：
  - `file`
  - `title`
  - `collection`
  - `domain`
  - `folder_path`
  - `tags`
  - `source_url`
  - `published`
  - `linked_kg_ids`
- 响应：

```json
{
  "upload_id": "upl_20260515_xxx",
  "file_name": "城市NOA技术综述.md",
  "stored_path": "/app/data/kb_uploads/upl_20260515_xxx.md",
  "size": 128930,
  "status": "uploaded"
}
```

**2. 触发导入任务**
- `POST /api/v1/kb/ingest`
- 作用：把上传文件或 manifest 送入导入管线
- 请求体：

```json
{
  "source_type": "upload",
  "upload_ids": ["upl_20260515_xxx"],
  "collection": "public.structured_tech.autonomous_driving",
  "defaults": {
    "domain": "structured_tech",
    "folder_path": "02-知识库/智能驾驶",
    "published": true,
    "source": "manual_upload",
    "language": "zh"
  },
  "options": {
    "chunk_mode": "markdown_heading",
    "chunk_size": 1200,
    "chunk_overlap": 150,
    "sync_cache": true,
    "project_id": "__all__",
    "skip_if_checksum_same": true
  }
}
```

- 响应：

```json
{
  "job_id": "ing_20260515_101500_a1b2c3",
  "status": "queued"
}
```

**3. 查询导入任务状态**
- `GET /api/v1/kb/ingest-jobs/{job_id}`
- 响应：

```json
{
  "job_id": "ing_20260515_101500_a1b2c3",
  "status": "running",
  "collection": "public.structured_tech.autonomous_driving",
  "doc_total": 12,
  "doc_succeeded": 8,
  "doc_failed": 0,
  "chunk_upserted": 126,
  "errors": []
}
```

**4. 批量发布或下线**
- `POST /api/v1/kb/publish`
- 作用：切换一批文档 `published` 状态，不重新导入正文
- 请求体：

```json
{
  "doc_ids": ["autodrive_001", "autodrive_002"],
  "published": true,
  "collection": "public.structured_tech.autonomous_driving"
}
```

- 响应：

```json
{
  "updated": 2,
  "published": true
}
```

**API 兼容建议**
- 不要替代现有 `POST /api/v1/kb/cache/sync`
- 新导入 API 成功后内部调用现有 sync 接口或直接复用 `kb_cache_service.sync_from_external()` 的逻辑
- `/knowledge` 页面短期不需要大改，只要新增上传入口和任务进度展示即可

**建议的数据模型补充**
- 建议新增一张 `kb_ingest_job` 表，字段如下：
  - `id`
  - `source_type`
  - `collection`
  - `status`
  - `payload_json`
  - `result_json`
  - `created_at`
  - `updated_at`
  - `created_by`
- 建议新增一张 `kb_source_file` 表，字段如下：
  - `id`
  - `file_name`
  - `stored_path`
  - `checksum`
  - `mime_type`
  - `size`
  - `created_at`

**状态机建议**
- `uploaded`
- `queued`
- `running`
- `completed`
- `partial_success`
- `failed`
- `cancelled`

**权限与治理建议**
- 上传不等于发布
- 默认建议 `published=false`，由治理人员确认后发布
- `internal` scope collection 默认不进入执行侧
- 删除文档建议先做“逻辑下线”，不要第一版就物理删 chunk

**推荐落地顺序**
- 第 1 步：先做离线脚本 `scripts/kb_ingest.py`
- 第 2 步：补 `kb_ingest_job` 表和 `POST /api/v1/kb/ingest`
- 第 3 步：补 `POST /api/v1/kb/upload`
- 第 4 步：前端 `/knowledge` 增加“上传文档”和“导入任务”面板
- 第 5 步：最后补“发布/下线”和版本治理

**最小可交付版本**
- 支持 Markdown/TXT 导入
- 支持 manifest JSON
- 支持写入 Chroma
- 支持同步 `kb_cache`
- 支持在 `/knowledge` 里看见目录树和搜索结果
- 支持导入任务状态查询

**一句话总结**
- 这套方案的核心是把“知识文档导入”设计成正式 ingestion 管线，而不是临时缓存导入；存储主链写 Chroma，展示治理走 `kb_cache`，两者通过统一 metadata 合同保持一致。
