我会把优化计划按“先收口基础架构，再打通联调，再做产品化加固”的顺序展开，给出分阶段目标、关键任务、交付物和验收标准。

**总体目标**
- 把项目从“原型与正式实现混合态”收敛为“可稳定运行、可持续迭代、可联调交付”的单一工程体系。
- 优化主线遵循三个原则：先统一入口与协议，再修复功能断点，最后补齐工程化与产品化能力。
- 所有优化以“减少不一致、降低维护成本、提高可验证性”为核心，不建议在此之前继续扩展新业务功能。

**优化原则**
- 单一事实来源：后端只有一个启动入口、一套路由规范、一套环境变量约定。
- 前后端契约优先：API 路径、请求字段、响应结构、错误语义先对齐，再谈页面增强。
- 真实链路优先：优先替换 mock fallback，保留 mock 只能作为显式开发开关。
- 可回归优先：每完成一阶段，都要有最小可验证的测试或联调清单。
- 渐进式重构：避免一次性大改，按阶段逐步收口。

**阶段 0：基线冻结**
- 目标：建立当前版本的事实基线，避免边改边漂移。
- 任务：梳理唯一运行方式、接口清单、页面清单、环境变量清单、数据库模型清单。
- 任务：明确当前“已上线能力”“半成品能力”“纯原型能力”三类边界。
- 任务：形成一份系统契约文档，作为后续修复的唯一依据。
- 交付物：`项目现状清单`、`API 对照表`、`页面与接口映射表`、`环境变量表`。
- 验收：团队能用一份文档说明系统如何启动、哪些接口可用、哪些页面依赖 mock。

**阶段 1：架构收口**
- 目标：统一后端应用入口、配置方式和路由规范，消除系统级歧义。
- 任务：在 `main.py` 与 `backend/__init__.py` 中确定唯一 FastAPI 启动入口。
- 任务：统一是否采用 `/api/v1` 前缀，并让前端、文档、Docker、README 全部一致。
- 任务：统一数据库配置来源，禁止代码中硬编码数据库地址。
- 任务：统一 CORS、健康检查、中间件、异常处理、响应格式的生效路径。
- 任务：确定 `main:app` 或 `backend:app` 为唯一启动方式，其他入口转为兼容壳或删除。
- 交付物：统一后的启动入口、配置模块、启动文档。
- 验收：本地、Docker、后续 CI 都使用同一入口且行为一致。

**阶段 2：接口契约对齐**
- 目标：修复前后端最核心的不一致，让主业务链路真正可联调。
- 任务：统一前端所有 API 基地址，改为单一 `api client` 或统一 `fetch wrapper`。
- 任务：移除前端页面中所有 `http://localhost:8000` 硬编码，改用环境变量。
- 任务：修复页面路由不一致，如 `/workspace` 与 `/workshop`。
- 任务：修复技能市场接口不一致，如 `/skills/market`、`/skills/install` 与后端实际定义不匹配。
- 任务：修复知识库页面接口路径、参数名、返回结构与后端的偏差。
- 任务：统一前后端的实体字段命名，如 `audience`、`target_audience`、`constraints` 的表达方式。
- 交付物：统一 API 封装层、前后端接口对照文档、打通后的页面链路。
- 验收：项目管理、技能管理、输出工坊、知识库四条主链路可以真实调用，不依赖页面内 mock。

**阶段 3：后端功能修复**
- 目标：修复当前后端中会直接导致运行失败或行为异常的问题。
- 任务：修复 `skills_store` 中数据库依赖注入缺失的问题，统一使用 `Depends(get_db)`。
- 任务：修复 `skills/*` 中错误导入 `app.services.skill_loader` 的问题，统一改为正确路径。
- 任务：检查 `SkillLoader`、`SkillLifecycleService`、`SkillVersionService` 的调用链，补齐异常处理。
- 任务：核查技能安装、启用、禁用、配置修改、版本快照、卸载的数据库与文件系统一致性。
- 任务：确认 `kb_cache` 表的建表与查询逻辑在首次启动时稳定可用。
- 任务：校验增强健康检查中的数据库与飞书依赖检查逻辑是否正确。
- 交付物：可运行的技能系统、稳定的知识库降级机制、无阻断后端错误。
- 验收：后端核心路由能通过基本接口测试，且无明显启动级错误。

**阶段 4：前端页面收口**
- 目标：把前端从“展示原型”推进到“真实业务前台”。
- 任务：建立统一的 `services/api` 或 `lib/api` 层，所有页面禁止直接散落式 `fetch`。
- 任务：把 `projects`、`skills`、`knowledge`、`workshop` 页面数据流收敛到统一请求与错误处理机制。
- 任务：明确哪些页面允许 fallback，fallback 必须显式标识并可关闭。
- 任务：清理与真实 API 不一致的 mock 数据结构，避免类型漂移。
- 任务：统一页面级 loading、error、empty state 和 toast 提示策略。
- 任务：对 `Layout`、首页导航、详情跳转、返回路径做一次全链路梳理。
- 交付物：统一前端 API 调用层、统一页面状态处理、真实接口可驱动页面。
- 验收：用户从首页进入各主页面时，不再遇到明显的死链、假数据错位或接口 404。

**阶段 5：技能工坊与生成链路增强**
- 目标：把“Skill 驱动内容生成”打造为项目最稳定的核心能力。
- 任务：定义统一的 Skill 元数据规范，包括名称、描述、类别、输入 schema、输出 schema、版本。
- 任务：让 `workshop` 页面选择技能、输入上下文、接收 SSE 结果时严格匹配后端协议。
- 任务：明确 `Skill.generate()` 的标准输出结构，避免 `str/dict/list` 混用造成前端复杂分支。
- 任务：决定技能市场是走“静态目录 + 本地安装”，还是未来接真实远程源。
- 任务：把 `multi_skill_scheduler` 从潜在能力收敛为可落地能力，或者暂时下线隐藏。
- 任务：补齐技能运行失败、输入不合法、版本回滚失败等错误提示。
- 交付物：统一 Skill 规范、稳定的工坊生成接口、可维护的技能管理模型。
- 验收：任意内置技能都能被发现、加载、执行、展示，并且失败时能给出清晰错误。

**阶段 6：知识库能力增强**
- 目标：把知识库从“代理雏形”升级为稳定的检索与降级服务。
- 任务：统一知识库 API 的查询接口风格，避免同时存在多套近似路径和参数命名。
- 任务：明确外部 ChromaDB 的协议假设，补齐配置项与连通性文档。
- 任务：完善缓存同步策略，区分全量同步、增量同步、只读降级、手动触发。
- 任务：让 SSE 事件真正接入前端，而不是只停留在后端能力层。
- 任务：为知识库页面补齐集合列表、查询结果、详情查看的真实映射。
- 任务：定义知识库数据结构与前端展示结构的转换层。
- 交付物：稳定的 KB 查询链路、清晰的降级策略、可消费的 SSE 通知。
- 验收：外部 KB 可用时走实时查询，不可用时自动降级且前端能感知状态。

**阶段 7：对话与业务融合**
- 目标：把 `chat`、`create`、`skills`、`knowledge` 串成同一个产品闭环。
- 任务：明确 `chat` 页是独立依赖 `hermes-agent`，还是需要和本项目后端协同。
- 任务：把快速创作页传递的 `systemContext`、`opener` 与后端能力边界梳清。
- 任务：决定聊天是否需要引用项目、知识库、技能结果作为上下文来源。
- 任务：如果要走 MCP，明确 `backend/mcp_server.py` 的定位是内部工具层还是产品外部接口。
- 任务：统一“对话生成”和“工坊生成”的用户体验与结果落地方式。
- 交付物：对话体系定位文档、上下文注入方案、跨模块业务闭环设计。
- 验收：用户可以从项目或快速创作进入对话，并获得一致的内容生成体验。

**阶段 8：工程化与质量保障**
- 目标：让项目具备持续开发和稳定交付的工程基础。
- 任务：修复 CI 配置与当前仓库结构不一致的问题。
- 任务：补齐后端最小测试集，优先覆盖 `projects`、`skills_store`、`workshop`、`kb`。
- 任务：补齐前端最小类型校验与关键页面交互测试。
- 任务：统一 lint、typecheck、test、build 命令入口。
- 任务：完善 Dockerfile、`docker-compose.yml`、环境变量说明和本地启动脚本。
- 任务：建立错误日志、请求日志、关键事件日志的最小观测能力。
- 交付物：可工作的 CI、稳定的构建流程、基础测试集、标准化 README。
- 验收：每次提交都能自动完成安装、检查、构建和核心测试。

**阶段 9：产品化与运营能力**
- 目标：把系统从“开发可用”推进到“业务可交付”。
- 任务：梳理飞书通知、OAuth、机器人、文件上传的真实业务场景与权限模型。
- 任务：确认项目、输出物、模板、技能的业务流转状态是否与数据库设计一致。
- 任务：补齐“生成结果如何保存、如何关联项目、如何反馈优化”的闭环。
- 任务：为管理员与普通用户设计最小权限边界。
- 任务：建立版本发布、数据库迁移、回滚预案。
- 交付物：业务闭环方案、权限策略、上线准备清单。
- 验收：系统不仅能生成内容，还能沉淀、追踪、通知和复用。

**优先级排序**
- `P0`：统一入口、统一路由前缀、修复前后端接口不一致、修复技能导入错误、修复数据库依赖注入、清理硬编码地址。
- `P1`：替换关键页面 mock、统一 API 层、稳定知识库降级、打通工坊链路、修复 CI。
- `P2`：对话体系融合、MCP 战略定位、飞书能力产品化、权限和发布体系。

**建议实施节奏**
- 第 1 周：完成阶段 0、1、2，目标是系统“能一致地跑起来并能联调”。
- 第 2 周：完成阶段 3、4，目标是项目、技能、工坊、知识库主页面真实可用。
- 第 3 周：完成阶段 5、6，目标是生成链路和知识库链路稳定。
- 第 4 周：完成阶段 8 的测试与 CI 收口，并开始阶段 7、9 的产品化决策。
- 如果资源有限，建议先只做 `P0 + P1`，先把系统从不一致状态拉回可维护状态。

**每阶段验收口径**
- 能否用统一命令启动前后端。
- 能否从首页进入每条主链路且没有死链。
- 能否通过真实接口完成增删改查或生成。
- 能否在接口失败时看到清晰错误，而不是静默 fallback。
- 能否通过最小测试与 CI 验证核心能力未回退。

**最大风险**
- 最大技术风险不是单点 bug，而是“双入口、双规范、双实现”的长期并存。
- 最大产品风险是前端展示逻辑已经假定了很多不存在的后端契约。
- 最大工程风险是当前 CI、文档、目录结构、运行方式已经发生漂移，继续叠加功能会加速失控。

**推荐执行顺序**
- 第一优先：统一后端入口和 API 规范。
- 第二优先：统一前端 API 调用和页面路由。
- 第三优先：修复技能系统与工坊链路。
- 第四优先：知识库真实联调。
- 第五优先：测试、CI、文档和发布流程。
- 第六优先：飞书、MCP、对话融合等增强能力。

**我建议的落地方式**
- 不要一次性全面重写。
- 以“架构收口 PR”“接口对齐 PR”“技能链路 PR”“知识库链路 PR”“工程化 PR”分批推进。
- 每个 PR 都要求同时更新代码、文档和最小验证脚本，避免再次出现实现与文档漂移。
