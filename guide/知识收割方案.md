规划：
*知识收割（Knowledge Harvesting）**的工作流设计：
## 现状分析

| 维度 | 当前状态 |
|------|---------|
| **KB读取** | ✅ MCP工具有 `kb_query`、`kb_get_entry` |
| **KB写入** | ❌ 没有MCP写入工具（只有查询） |
| **后端写入API** | FastAPI后端(172.18.0.4:8000)存在，但尚未暴露为MCP工具 |

---

## 三种方案

### 方案A：手动确认写入（推荐，最可靠）

**流程：**
```
对话中识别技术信息 → 询问用户"是否存入知识库？" → 用户确认 → 调用KB写入API
```

**需要新增：**
1. 一个调用后端 `POST /api/v1/kb/entries/add` 的 MCP工具（`kb_add_entry`）
2. 一个 `knowledge-harvest` skill，定义"识别→提取→确认→写入"的流程

**优点：** 质量可控、用户主导、无噪音
**缺点：** 需要用户主动参与
          
**结论**
- 你的判断基本正确，`方案A：手动确认写入` 仍然是当前项目里最稳的路线。
- 但我建议做一个关键调整：`knowledge-harvest` 不要先做成现有 `Workshop Skill` 类型，而应做成“对话层流程策略 + MCP 写工具”的组合。
- 原因是当前 `Workshop Skill` 本质是一次性 `generate(context)` 执行，不适合“识别 -> 提取 -> 询问确认 -> 再写入”的多轮交互流程，可参考 [workshop_tools.py](file:///Volumes/Lexar/git/03T/TPDHermes/backend/tools/workshop_tools.py#L216-L299) 和 [skill_loader.py](file:///Volumes/Lexar/git/03T/TPDHermes/backend/services/skill_loader.py#L28-L62)。

**现状校验**
- MCP 侧确实只有读能力，当前暴露的 KB 工具只有 `kb_query`、`kb_list_collections`、`kb_get_entry`，见 [mcp_server.py](file:///Volumes/Lexar/git/03T/TPDHermes/backend/mcp_server.py#L28-L67)。
- Hermes 侧也只白名单放开了这几个 KB 工具，没有写入工具，见 [config.yaml](file:///Volumes/Lexar/git/03T/TPDHermes/deploy/hermes-agent/config.yaml#L6-L29)。
- 后端我没有找到你写的现成 `POST /api/v1/kb/entries/add` 实现；当前已有的“写入链路”是 `upload`、`ingest`、`publish` 这套文档导入流程，见 [kb_ingest.py](file:///Volumes/Lexar/git/03T/TPDHermes/backend/routes/kb_ingest.py#L69-L281)。
- 这说明现在缺的不是“能不能写 KB”，而是“缺一个面向对话摘录的原子写入入口”。

**推荐设计**
- 推荐架构：`对话识别策略` + `kb_add_entry MCP tool` + `后端 KB entry add API`。
- 推荐流程：
  1. 对话中识别到可沉淀知识。
  2. 先提炼成结构化草稿。
  3. 向用户展示草稿并确认是否入库。
  4. 用户确认后调用 `mcp_tphermes_kb_add_entry`。
  5. 后端写入 KB，并返回 `entry_id/doc_id/chunk_count`。
  6. 可选再提示“是否立即发布”或默认以草稿态保存。
- 我建议默认“先写入未发布草稿”，把 `published=false` 作为第一版默认值，后续复用现有发布接口做人工审核发布，见 [kb_ingest.py](file:///Volumes/Lexar/git/03T/TPDHermes/backend/routes/kb_ingest.py#L246-L281)。

**为什么不建议先做成 Workshop Skill**
- 当前 `skills/` 下的能力都是模板生成型技能，输入是一个 `context`，输出是一次性结果，不负责用户确认，也不负责工具调用编排，见 [benchmark_skill/__init__.py](file:///Volumes/Lexar/git/03T/TPDHermes/skills/benchmark_skill/__init__.py#L168-L242)。
- 所以“knowledge-harvest”如果放进现有 `Workshop` 体系，会很别扭，最后还是要靠对话层额外补确认逻辑。
- 更合适的定位是：
  - `策略/提示层`：何时触发知识收割、如何展示草稿、何时询问确认。
  - `MCP 工具层`：真正执行写入。
- 等 MVP 稳定后，再考虑把“候选提取模板”沉淀成一个辅助 skill，而不是把整个流程都塞进 skill。

**`kb_add_entry` 的实现建议**
- 第一版工具名直接用 `kb_add_entry`，保持和现有 `kb_query` 命名风格一致。
- MCP 暴露位置仍放在 [mcp_server.py](file:///Volumes/Lexar/git/03T/TPDHermes/backend/mcp_server.py)。
- 后端实现建议放在新的 `backend/tools/kb_tools.py` 扩展函数或拆成 `backend/services/kb_write.py`。
- 最重要的建议：第一版不要绕开现有 ingest 链路直接手写 Chroma upsert。
- 更稳的做法是：`kb_add_entry` 在服务端把摘录内容组装成一份临时 markdown/manifest，然后复用现有 ingestion 核心 [kb_ingest_core.py](file:///Volumes/Lexar/git/03T/TPDHermes/backend/services/kb_ingest_core.py#L147-L388)。
- 这样可以直接复用：
  - metadata 校验
  - chunk 切分
  - Chroma upsert
  - 缓存同步
  - stale chunk 清理
- 这比新开一条“直接写 Chroma”的旁路更安全，也更符合你项目当前的知识库架构。

**推荐 API 契约**
- 建议后端新增 `POST /api/v1/kb/entries`，不要用 `/entries/add`，REST 风格更清晰。
- 请求体建议最少包含：
  - `collection_name`
  - `project_id`
  - `title`
  - `content`
  - `summary`
  - `tags`
  - `domain`
  - `source`
  - `source_type="conversation_harvest"`
  - `published=false`
  - `metadata`
- 其中 `metadata` 建议补这些字段：
  - `conversation_id`
  - `message_ids`
  - `harvested_from_user_confirmed=true`
  - `confidence`
  - `dedupe_key`
  - `created_by`
- 返回结构建议统一为：
  - `ok`
  - `message`
  - `entry_id`
  - `doc_id`
  - `collection_name`
  - `chunk_count`
  - `published`
  - `trace_id`

**质量控制**
- 只允许收割“事实型、可复用、非瞬时”的信息，不要把临时猜测、主观闲聊、未验证结论写进去。
- 增加去重：基于 `title + normalized_content` 计算 `dedupe_key`，重复内容只提示已存在。
- 增加最小置信度阈值：低于阈值只给用户建议，不主动弹确认。
- 上游 KB 不可用时直接失败并返回 `readonly/unavailable`，不要假成功。当前 KB 代理本身就有只读降级语义，见 [kb_proxy.py](file:///Volumes/Lexar/git/03T/TPDHermes/backend/services/kb_proxy.py#L33-L42)。

**推荐状态机**
- `detected`：识别到候选知识。
- `drafted`：提取出标题、摘要、正文、标签、归属 collection。
- `awaiting_confirm`：向用户展示草稿，等待确认。
- `confirmed`：用户允许入库。
- `written`：调用 `kb_add_entry` 成功。
- `published`：可选审核发布。
- 第一版只做到 `written` 就够了，`published` 可以后置。

**落地顺序**
- 第 1 步：新增后端 `kb_add_entry` API，内部复用 ingest 核心。
- 第 2 步：在 [mcp_server.py](file:///Volumes/Lexar/git/03T/TPDHermes/backend/mcp_server.py) 暴露 `kb_add_entry`。
- 第 3 步：在 [config.yaml](file:///Volumes/Lexar/git/03T/TPDHermes/deploy/hermes-agent/config.yaml#L12-L29) 把 `kb_add_entry` 加入 `include`。
- 第 4 步：补一段对话层提示策略，定义何时提议“是否存入知识库”。
- 第 5 步：做 3 个验收场景：
  - 用户确认后成功写入
  - 重复知识不重复写
  - KB 不可用时明确失败提示

**一句话建议**
- `方案A` 继续推进，但实现形态应当是“对话层确认流程 + MCP 写工具”，而不是先把整个流程硬塞进现有 `Workshop Skill` 体系。
