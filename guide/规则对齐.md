## 结论先说
在 `workshop` 入口下，选中的 skills 可以做到比较严格约束（接近强制）；  
在 `chat/create` 入口下，skills 目前更多是“提示约束”，不是完全硬限制。

## 1) 选中的 skills 是怎么进入执行链的
- 场景配置存于 `scenario_profiles.skills_policy_json`（`backend/models/scenario_profile.py`）。
- 请求进来后，`assemble_payload` 会把项目默认、场景策略、请求 overrides 合并成 `payload.skills`（`backend/services/orchestration_service.py`）。
- 如果是 `workshop` 入口，会被再次强制成：
  - `mode=manual_only`
  - `allow_agent_free_choice=False`
  （同文件里有显式覆盖逻辑）

## 2) “严格执行”具体怎么落地
在 `backend/routes/tasks.py` 有几道硬闸：

- **白名单必须存在**：`workshop` 下 `payload.skills.allowed` 为空直接 400。
- **白名单技能必须可见可用**：逐个校验，不可见/不可加载直接 400。
- **真正执行时固定技能**：`workshop_skill = payload.skills.allowed[0]`，即服务端选定第一个技能执行。
- **Agent 模式还会回收工具结果**：如果 Hermes-agent 没调用 `workshop_generate` / `workshop_generate_from_kb`，会 424 失败（或按环境变量降级 direct）。

> 这点很关键：不是只靠 prompt 里说“请用某技能”，而是服务端在执行阶段和落库阶段都在兜底。

## 3) 模板输出物/文件如何保证
模板约束有两类：

- **输出模板策略（场景级）**  
  来自 `output_policy`（`template_id`、`required_sections`、`must_follow_template`），在 `backend/services/template_service.py` 做章节校验。  
  若 `must_follow_template=true` 且校验不通过，运行会变 `draft`，并且不会写入最终输出记录。

- **技能内模板（技能包级）**  
  `SkillLoader` 会读取 `skill.json` 的 `template` 字段并注入模板内容给 Skill 实例（`backend/services/skill_loader.py`）。  
  这是 Skill.generate 的“素材来源”，不是平台级的最终验收规则。

最终产物不是磁盘文件，而是数据库输出物：
- 运行记录：`orchestration_runs`
- 产出物：`outputs`（模型 `backend/models/output_asset.py`）
- 写入逻辑：`backend/services/run_log_service.py`

## 你问的核心逻辑：TPDHermes Skills vs Hermes-agent 内嵌 Skills

这是两套并行机制，Hermes-agent 都能“用到”，但路径不同：

- **A. TPDHermes Skills（你平台的技能）**  
  - 存放/加载：`TPDHermes backend` 的 `skills/`，由 `SkillLoader` 加载  
  - 调用方式：Hermes-agent 通过 MCP 工具 `workshop_generate` / `workshop_generate_from_kb` 间接调用  
  - 权限控制：在 TPDHermes 后端按 `owner_id`、`enabled`、可见性规则控制

- **B. Hermes-agent 内嵌 Skills（agent 自带）**  
  - 存放：`hermes-agent` 自身的 `skills/`（以及可选 `optional-skills/`）  
  - 调用方式：agent 内部技能系统直接加载执行，不经过 TPDHermes 的 `workshop_generate`  
  - 权限边界：由 Hermes-agent 自己的配置/工具集控制，不走你这边 `owner_id` 规则

**结论一句话：**  
Hermes-agent 既能调用“自己的内嵌 skills”，也能调用“TPDHermes 暴露的 workshop 技能工具”；两者不冲突，属于不同执行面。  
在 `workshop` 入口你们是偏强制走 TPDHermes skill 工具链；在 `chat/create` 入口则仍有较多 agent 自主空间。

---

当前系统里，`公共工作区 skills` 和 `个人 skills` 的区分与调用，主要靠 **`owner_id` + 可见性过滤**，不是靠目录名。

- `公共技能`：`owner_id=""`（空），所有用户可见可调用。
- `个人技能`：`owner_id="<user_id>"`，仅该用户（或全局管理员）可见可调用。
- 前端“公共/我的技能”分区是展示层，真正生效的是后端过滤规则。

调用时的实际行为：

- **列表接口**（如 `GET /skills`、`/ws/skills`、`mcp workshop_list_skills`）  
  会按当前用户做过滤：只返回 `owner_id=""` 或 `owner_id=当前用户` 的技能，并且要求 `enabled=1` 且可加载。
- **执行接口**（`workshop_generate` / `tasks/execute`）  
  最终也会校验技能是否对当前用户可见；`workshop` 场景还会按 `allowed` 白名单执行（工坊固定取 `allowed[0]`）。

你这次“看不到个人技能”的根因就是：请求身份是 `auto_*`，但技能归属是 `default`，两边 user_id 不一致，被过滤掉。
