**方案概述**
- 目标是将 `TPDHermes` 从“前端拼接上下文 + 后端代理聊天”的过渡态，升级为“以编排为核心、由 `Hermes-agent` 统一执行”的业务系统。
- 编排对象聚焦三类核心资产：`技术领域`、`知识范围`、`输出模板`，并补充 `项目`、`场景`、`技能策略`、`执行策略`、`输出物沉淀`。
- 设计原则是 `TPDHermes` 负责定义边界与规则，`Hermes-agent` 负责推理、检索、调用工具和组织输出。
- 当前系统基础可复用，包括项目管理、知识库代理、技能系统、聊天代理与 MCP 工具暴露，[projects.py](file:///Volumes/Lexar/git/03T/TPDHermes/backend/routes/projects.py)、[kb.py](file:///Volumes/Lexar/git/03T/TPDHermes/backend/routes/kb.py)、[workshop.py](file:///Volumes/Lexar/git/03T/TPDHermes/backend/routes/workshop.py)、[mcp_server.py](file:///Volumes/Lexar/git/03T/TPDHermes/backend/mcp_server.py)。

**一、建设背景**
- 当前 `/chat` 链路由前端先拉取项目、知识库、技能信息，再把摘要文本注入用户消息，这种方式可联调，但职责边界不清晰，[chat-context.ts](file:///Volumes/Lexar/git/03T/TPDHermes/src/lib/chat-context.ts)、[chat/page.tsx](file:///Volumes/Lexar/git/03T/TPDHermes/src/app/chat/page.tsx)。
- 当前 `/create` 只是静态场景卡片页，本质是“预设提示词跳转器”，还不是编排中心，[create/page.tsx](file:///Volumes/Lexar/git/03T/TPDHermes/src/app/create/page.tsx)。
- ~~当前 `/workshop` 直接调用本地 skill 生成，不经过 Agent 编排~~ **（2026-05 已落地）**：默认 `WORKSHOP_EXECUTION_MODE=agent`，经 Hermes-agent 调用 `workshop_generate*` MCP 工具，产出正文由 `tool_capture_json` 落库；`direct` 保留作开发降级，[workshop/page.tsx](file:///Volumes/Lexar/git/03T/TPDHermes/src/app/workshop/page.tsx)、[tasks.py](file:///Volumes/Lexar/git/03T/TPDHermes/backend/routes/tasks.py)。
- 当前项目模型缺少对技术范围、知识范围、模板绑定、输出物版本等核心业务概念的表达，[project.py](file:///Volumes/Lexar/git/03T/TPDHermes/backend/models/project.py)。
- `schema.sql` 虽预留 `templates` 和 `outputs`，但尚未真正接入运行时主链路，[schema.sql](file:///Volumes/Lexar/git/03T/TPDHermes/schema.sql#L25-L58)。

**二、方案目标**
- 建立统一的“编排模型”，覆盖项目、场景、技术、知识、模板、技能、执行与输出物。
- 将前端的“显式文本注入”升级为“结构化编排参数提交”。
- 让 `Hermes-agent` 成为单一执行中枢，统一承担检索、技能调用、模板约束与最终生成。
- 将结果从“聊天回复”升级为“可回溯、可复用、可评审的输出物”。
- 支持从 `项目`、`快速创作`、`对话`、`工坊` 多入口进入同一套执行框架。
- 为后续“专用 Skill / 公共 Skills”“专用知识 / 公共知识”“权限控制”“审计留痕”预留标准化接口。

**三、总体设计**
- 总体思路是：`前端声明需求 -> TPDHermes 组装编排负载 -> Hermes-agent 按编排执行 -> 结果回写输出物与执行记录`。
- `TPDHermes` 不再直接“替 Agent 思考”，而是负责发布一份结构化任务合同。
- `Hermes-agent` 根据合同决定调用哪些 MCP tool、知识库接口、技能能力与模板规则。
- 聊天、工坊、快捷创作都归一为同一个“任务执行接口”，只是入口 UI 不同。
- 模板不再只是页面上的“文案模板选择”，而是带结构、字段、章节和校验规则的正式数据资产。

**四、职责边界**
- `TPDHermes` 负责：项目管理、场景管理、编排配置、知识域边界、模板管理、技能策略、任务提交、结果持久化、评审反馈。
- `Hermes-agent` 负责：理解任务、选择工具、检索知识、组合技能、遵循模板、执行多轮推理、生成可交付内容。
- `MCP Server` 负责：以标准工具协议暴露 `projects`、`kb`、`workshop` 等能力给 Agent，[mcp_server.py](file:///Volumes/Lexar/git/03T/TPDHermes/backend/mcp_server.py)。
- `前端` 负责：收集业务输入、展示编排预览、发起执行、展示结果与历史，不再负责拼装长提示词。

**五、核心编排模型**
- 建议新增统一对象：`OrchestrationPayload`。
- 该对象是 `TPDHermes` 与 `Hermes-agent` 之间的正式协议，也是运行时最核心的数据结构。
- 推荐结构如下：

```json
{
  "request_id": "req_20260514_xxx",
  "entrypoint": "chat",
  "project": {
    "id": "proj_xxx",
    "name": "智能座舱技术推广项目",
    "background": "面向车企客户输出技术推广材料",
    "audience": "客户技术负责人、产品经理",
    "constraints": {
      "tone": "professional",
      "length": "1500-2500",
      "language": "zh-CN"
    }
  },
  "scenario": {
    "id": "tech-solution",
    "name": "技术方案说明",
    "goal": "生成可对外沟通的技术方案材料",
    "conversation_mode": "task_oriented"
  },
  "domain": {
    "technical_scope": [
      "智能座舱",
      "语音交互",
      "车载大模型"
    ],
    "business_scope": [
      "方案介绍",
      "客户沟通",
      "优势阐述"
    ],
    "terminology_policy": "tpd_standard"
  },
  "knowledge": {
    "mode": "restricted",
    "collections": ["tpd_docs", "product_specs"],
    "project_bound": true,
    "top_k": 5,
    "fallback_policy": "cache_allowed"
  },
  "skills": {
    "mode": "allowed_list",
    "allowed": ["a4_skill", "speech_skill"],
    "preferred": ["a4_skill"],
    "allow_agent_free_choice": false
  },
  "output": {
    "template_id": "tpl_solution_v1",
    "format": "markdown",
    "must_follow_template": true,
    "required_sections": ["背景", "目标", "方案设计", "优势", "风险"],
    "validation_rules": {
      "must_have_headings": true,
      "must_cite_sources": true
    }
  },
  "execution": {
    "stream": true,
    "trace": true,
    "save_output": true,
    "save_run_log": true
  },
  "user_input": {
    "message": "请基于当前项目生成一版面向客户的技术方案说明。"
  }
}
```

**六、编排字段定义**
- `project`：定义项目上下文与长期约束，是所有入口共享的业务主实体。
- `scenario`：定义任务意图与协作模式，例如“技术方案”“PRD”“知识问答”“发布会发言稿”。
- `domain`：定义技术与业务边界，控制 Agent 的话题范围、术语体系和表达口径。
- `knowledge`：定义可访问的知识集合、检索策略、是否允许跨项目、是否允许降级缓存。
- `skills`：定义技能白名单、偏好顺序、是否允许 Agent 自由选择额外技能。
- `output`：定义模板、格式、章节要求、校验规则、是否必须严格遵守。
- `execution`：定义流式返回、调试跟踪、结果落库、日志留痕等运行时策略。
- `user_input`：定义本次用户输入，不与编排结构混杂。

**七、技术范围编排设计**
- 技术范围是强约束，不应只作为一段背景文本存在。
- 建议建立 `domain profiles` 概念，用结构化方式描述技术域。
- 每个 `domain profile` 包含：技术主题、禁用主题、术语规范、口径说明、优先知识库、推荐技能。
- 示例字段包括：`technical_scope`、`excluded_topics`、`terminology_policy`、`style_guidelines`、`citation_policy`。
- 这样 Agent 在执行时知道“可以谈什么、不可以谈什么、应该怎么表达”。
- 技术范围既可挂在项目上，也可由场景临时覆盖。
- 对于 TPD 场景，建议至少预置“智能座舱”“辅助驾驶”“数据平台”“研发效能”几类标准领域包。

**八、知识范围编排设计**
- 当前知识库是单代理服务加缓存降级，未来应升级为“知识访问策略层”，而不仅是查询接口，[kb_proxy.py](file:///Volumes/Lexar/git/03T/TPDHermes/backend/services/kb_proxy.py)。
- 知识范围应具备三类控制：`可访问集合`、`可访问粒度`、`检索策略`。
- `可访问集合` 用于限制 Agent 只查指定 collections。
- `可访问粒度` 用于限制是否跨项目、是否仅项目绑定知识、是否允许公共知识混入。
- `检索策略` 用于配置 `top_k`、重排序、缓存降级、引用保留规则。
- 建议新增 `knowledge policy` 实体，用于沉淀知识访问配置，而不是每次聊天临时选择一个 collection。
- 对外暴露给 Agent 的不是“页面上选中的知识库名称”，而是“本次任务允许访问的知识域策略”。

**九、输出模板编排设计**
- 输出模板应升级为第一类业务资产，而不是仅在工坊页面上用“模板类型”表达。
- 一个正式模板至少包含：模板 ID、名称、适用场景、输出格式、必填章节、可选章节、风格要求、字段约束、校验规则。
- 模板可分两层：`结构模板` 与 `内容模板`。
- `结构模板` 控制章节、字段、顺序、格式。
- `内容模板` 控制语气、长度、示例风格、引用方式。
- 模板应支持版本化，例如 `tpl_solution_v1`、`tpl_solution_v2`。
- Agent 执行时应显式接收到模板合同，而不是仅收到“请用 xxx 风格输出”的自然语言。
- 模板执行后应能校验结果是否满足结构要求，例如章节是否齐全、是否包含来源说明。

**十、技能策略设计**
- 当前技能是统一目录发现和本地调用，未来建议加入“编排级技能策略”作为上层控制，[skill_loader.py](file:///Volumes/Lexar/git/03T/TPDHermes/backend/services/skill_loader.py)。
- 技能策略至少应支持：`allowed list`、`preferred list`、`forbidden list`、`manual only`、`agent select`。
- `allowed list` 适合业务合规场景，只允许白名单技能被调用。
- `preferred list` 适合推荐型场景，优先使用指定技能，但允许兜底。
- `manual only` 适合必须由用户明确选择技能的工坊模式。
- 长期建议将技能分层为 `TPD 专用技能` 与 `公用技能` 两大类，并在编排中显式声明来源优先级。

**十一、执行流程设计**
- 标准流程建议统一为：创建任务、加载编排、Agent 执行、过程追踪、结果回写、人工评审。
- 详细链路如下：
- 第一步，用户从 `项目`、`快捷创作`、`对话`、`工坊` 任一入口进入。
- 第二步，前端只提交结构化请求，不预先把 KB 结果和项目摘要拼成提示词。
- 第三步，后端根据项目配置、场景配置、知识策略、模板策略生成 `OrchestrationPayload`。
- 第四步，后端把 `OrchestrationPayload` 与用户输入一起发送给 `Hermes-agent`。
- 第五步，`Hermes-agent` 解析编排结构，按约束调用 MCP tools 与内部推理。
- 第六步，Agent 生成结果后返回正文、引用来源、执行轨迹摘要、使用技能与知识信息。
- 第七步，TPDHermes 将结果写入 `outputs`，将执行快照写入 `runs`，供回看、复用、评审和追问。

**十二、建议的 Agent 协议**
- 建议不要继续沿用“把上下文正文拼进 user message”的方案。
- 建议后端构造统一协议，例如：

```json
{
  "model": "hermes-agent",
  "stream": true,
  "messages": [
    {
      "role": "system",
      "content": "你是 TPDHermes 编排执行代理。你必须优先遵循 orchestration 中的边界、模板和技能策略。"
    },
    {
      "role": "user",
      "content": "请基于当前任务生成内容。"
    }
  ],
  "extra": {
    "orchestration": {
      "...": "结构化编排内容"
    }
  }
}
```

- 如果 `Hermes-agent` 当前还不支持 `extra.orchestration`，可短期在 `system` 消息中嵌入一段严格标记的 JSON 块。
- 中期目标应是让 Agent 原生识别编排对象，而不是依赖文本提示工程。
- Agent 返回建议增加 `metadata` 字段，包括 `used_collections`、`used_skills`、`template_id`、`citations`、`run_id`。

**十九、运行时校验机制**
- 提交前校验：项目是否存在、模板是否可用、知识集合是否可访问、技能是否允许。
- 执行中校验：若 Agent 调用了不在白名单中的技能，应记录违规并阻断或降级。
- 结果校验：检查模板章节是否齐全、引用是否存在、输出格式是否匹配。
- 回写校验：只有通过基本校验的结果才写入 `outputs`，否则仅存为 `runs` 草稿。
- 人工校验：项目详情页支持审核、驳回、二次优化与版本对比。

- 保留现有 `mcp_server.py`，因为它已经提供了 Agent 可调用的项目、知识库、工坊工具，[mcp_server.py](file:///Volumes/Lexar/git/03T/TPDHermes/backend/mcp_server.py)。

**二十一、迁移路径**
- 第一阶段，定义编排数据结构与后端服务，不改动现有页面主交互。
- 第二阶段，在 `/chat` 引入“结构化编排请求”，短期仍可在后端把编排对象适配为 prompt 传给 Agent。
- 第三阶段，推动 `Hermes-agent` 原生支持 `orchestration` 协议字段。
- 第四阶段，将 `/create`、`/workshop` 全部并入统一任务执行接口。
- 第五阶段，打通 `templates`、`outputs`、`runs`，形成项目内闭环。
- 第六阶段，增加领域配置、知识策略、权限策略与评审流。

**二十二、分阶段实施建议**
- `P0`：落地 `OrchestrationPayload`、`orchestration_service`、`tasks/execute` 接口、模板表与输出物表。
- `P1`：改造 `/chat` 走编排执行链路，保留现有聊天 UI。
- `P1`：项目详情页接入真实输出物与运行记录。
- `P2`：改造 `/create` 为场景编排页，改造 `/workshop` 为编排生成页（**工坊 Agent 化已完成**，`/create` 待统一）。
- `P2`：支持模板校验、引用追踪、技能白名单策略。
- `P3`：实现专用/公共知识分层、专用/公共技能分层、审批与审计。

**二十三、风险与应对**
- 风险一：`Hermes-agent` 当前未必支持结构化编排字段。
- 应对：先由后端适配为受控 prompt，后续再升级 Agent 原生协议。
- 风险二：现有技能输出结构不统一，可能影响模板校验与结果收敛。
- 应对：定义统一 Skill 输出协议，逐步收敛 `str/dict/list` 混用现状。
- 风险三：知识库当前存在缓存降级模式，实时性不足，[项目现状清单.md](file:///Volumes/Lexar/git/03T/TPDHermes/guide/%E9%A1%B9%E7%9B%AE%E7%8E%B0%E7%8A%B6%E6%B8%85%E5%8D%95.md)。
- 应对：将知识策略中显式记录 `fallback_policy` 和 `knowledge_source`，避免结果来源不透明。
- 风险四：前端页面较多，改造容易出现双轨逻辑。
- 应对：先统一后端任务接口，再逐页切换前端。

**二十四、验收标准**
- 用户可在项目中配置技术范围、知识范围、默认模板，并在后续对话中自动生效。
- `/chat`、`/create`、`/workshop` 都调用同一个任务执行接口。
- `Hermes-agent` 能依据编排参数自动决定知识检索和技能调用，不再依赖前端拼接上下文。
- 每次结果都能回写为 `output`，并关联 `project`、`template`、`run`。
- 项目详情页可查看输出历史、引用来源、使用模板和技能摘要。
- 系统可区分“任务编排配置”与“用户自然语言输入”。
- 模板约束能对输出结果进行基础校验并给出可见反馈。

**二十五、预期收益**
- 业务一致性更强，多个入口生成的结果口径一致。
- 架构职责更清晰，前端不再承担提示工程职责。
- 结果可追踪，可复现，可治理，适合企业级交付。
- 项目成为真正的业务中心，而不是简单 CRUD 容器。
- 技术域、知识域、模板域沉淀为长期资产，可跨项目复用。
- 为后续接入权限、评审、发布、飞书协同等能力建立稳定基础。

**结论**
- 这套方案的本质不是“给 Agent 更多上下文”，而是“让 `TPDHermes` 用结构化编排定义任务合同，再交给 `Hermes-agent` 执行”。
- 对当前项目而言，这是一条连续演进路径，不需要推倒重来，现有项目、知识库、技能、MCP、聊天代理都可以复用。
- 最关键的第一步不是改 UI，而是先确立 `OrchestrationPayload + 任务执行接口 + 模板/输出物模型` 这三件事。
