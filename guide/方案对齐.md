

**核心定义**
- 主流程只有两条生产路径：
- `项目 -> 对话创作 -> 输出`
- `项目 -> 场景输出 -> 输出结果`
- 其他模块都不直接承担“生产结果”的职责，而是为这两条主链路提供边界、能力和资源。

**一、整体业务架构对齐**

建议把系统重定义为：

- `项目管理` 是业务主入口
- `对话创作` 是通用创作入口
- `场景输出` 是标准化、模板化输出入口
- `场景编排` 是规则定义中心
- `知识管理` 是公共知识供给中心
- `技能管理` 是公共与个人技能供给中心

也就是说：

- 用户先进入`项目`
- 在项目下选择：
  - 直接进入`对话创作`
  - 或进入`场景输出`
- `对话创作` 和 `场景输出` 都由 `Hermes-agent` 执行
- 执行时会引用：
  - 项目上下文
  - 场景合同
  - 公共知识库
  - 公共技能 / 个人技能
- 最终沉淀为项目下的`输出结果`

---

**二、核心业务流程**

**流程 1：项目 -> 对话创作 -> 输出**
适合：
- 需求不确定
- 需要多轮探索
- 需要先澄清再产出

推荐链路：
1. 创建或进入项目
2. 查看项目描述、附件、历史输出
3. 打开`对话创作`
4. 以项目上下文为基础进行多轮对话
5. Hermes-agent 按需要调用公共知识和技能
6. 用户确认后，将结果保存为项目输出

这个流程的特点：
- 更灵活
- 更适合探索式协作
- 输出不一定严格模板化，但可选择套用模板

---

**流程 2：项目 -> 场景输出 -> 输出结果**
适合：
- 任务明确
- 输出类型固定
- 需要标准化交付

推荐链路：
1. 创建或进入项目
2. 选择一个已编排好的场景
3. 补充本次任务输入
4. Hermes-agent 按场景合同执行
5. 生成结构化结果
6. 自动回写项目输出历史

这个流程的特点：
- 更规范
- 更适合批量与复用
- 输出质量更稳定，更接近企业交付物

---

**三、模块职责对齐**

**1. 项目管理**
定位：
- 业务主容器
- 上下文主入口
- 输出沉淀中心

建议包含：
- 项目描述
- 项目背景
- 项目附件
- 目标受众
- 项目约束
- 历史输出
- 运行记录

项目管理不负责定义技能和知识策略细节，但它决定：
- 当前任务属于哪个业务上下文
- 哪些输出结果归属当前项目
- 哪些附件和历史结果可作为参考

一句话：
- `项目管理` 管的是“这件事是什么、材料是什么、结果沉淀到哪里”。

---

**2. 场景编排**
定位：
- 场景规则设计中心
- 输出合同定义中心

建议包含：
- 场景说明
- 场景目标
- 关联 skill
- 关联知识策略
- 定义输出模板
- 定义风格与校验规则
- 形成合同

这里最关键的是“合同”概念。

一个场景最终产出的不是正文，而是：

- 这个场景怎么执行
- 可以调用哪些 skill
- 输出必须长什么样
- 应该参考哪些知识

一句话：
- `场景编排` 管的是“这类任务应该怎么做”。

---

**3. 知识管理**
定位：
- 公共知识库管理中心

你当前这版设计里，知识管理建议先聚焦在：
- `公共知识库`

建议能力：
- 知识集合管理
- 文档上传
- 文档清洗
- 集合分类
- 检索测试
- 集合启停
- 场景关联

注意这里的边界：
- 知识管理负责“供给知识”
- 不直接负责“某个项目怎么使用知识”
- 项目 / 场景执行时再决定调用哪些集合

一句话：
- `知识管理` 管的是“系统有哪些可用的公共知识”。

---

**4. 技能管理**
定位：
- 通用能力与个人能力管理中心

建议拆成两部分：

- `公共技能库`
- `个人 Skills`

建议能力：
- 查看技能列表
- 安装 / 启用 / 禁用技能
- 上传个人 skill
- 查看 skill 描述、版本、配置
- 验证 skill 可执行性

其中：
- 公共技能库：平台统一提供、治理
- 个人 skills：用户自定义上传，供个人或指定项目使用

这部分很重要，因为它决定系统的能力扩展方式。

一句话：
- `技能管理` 管的是“系统和个人有哪些可调用能力”。

---

**四、建议的最终页面结构**

基于你的思路，首页建议只保留这些一级入口：

- `项目管理`
- `对话创作`
- `场景输出`
- `场景编排`
- `知识管理`
- `技能管理`

但实际使用顺序应突出：

- 主入口：`项目管理`
- 生产入口：`对话创作`、`场景输出`
- 配置入口：`场景编排`、`知识管理`、`技能管理`

也就是说，配置类页面不是第一业务入口，项目才是。

**六、系统运行时职责**

建议运行时统一成下面这个模式：

**项目侧提供**
- 项目描述
- 项目附件
- 历史输出参考

**场景侧提供**
- 场景说明
- 关联 skill
- 输出模板合同

**知识侧提供**
- 公共知识集合

**技能侧提供**
- 公共技能
- 个人技能

**Hermes-agent 负责**
- 理解当前任务
- 读取项目上下文
- 按需装载场景合同
- 检索公共知识
- 调用公共/个人 skill
- 输出最终结果
- 回写输出物与运行记录

**七、与你当前系统的对齐建议**

按照你这套思路，前后端应该进一步统一成下面几个原则：

**原则 1**
- `项目` 是唯一业务主入口
- `对话创作` 和 `场景输出` 都应优先从项目进入

**原则 2**
- `场景编排` 不直接生产结果
- 它只产出“合同”

**原则 3**
- `知识管理` 与 `技能管理` 是公共资源中心
- 不直接承担项目执行入口职责

**原则 4**
- `场景输出` 必须受场景合同约束
- 不能再让工坊自由定义全部技能和模板策略

**原则 5**
- `对话创作` 和 `场景输出` 的结果都要回写项目历史输出

**八、推荐的产品文案定义**

你可以直接把系统文档里的定义写成下面这样：

- `项目管理`：管理项目描述、项目附件、历史输出和执行记录，是业务工作的主入口。
- `对话创作`：基于项目上下文进行多轮创作与协作，适合探索式任务与开放式内容生成。
- `场景输出`：基于项目与场景合同执行标准化生成，适合固定类型、模板化、可复用的交付输出。
- `场景编排`：定义场景说明、关联 skill、输出模板和执行合同，是场景输出的规则来源。
- `知识管理`：管理公共知识库，为创作与输出提供检索支撑。
- `技能管理`：管理公共技能库和个人 skills，为系统提供可扩展执行能力。

---

**九、一句话总结构**

按你现在这版思路，最合理的系统抽象是：

- `项目` 负责承载业务
- `对话创作 / 场景输出` 负责生产结果
- `场景编排 / 知识管理 / 技能管理` 负责提供规则、知识和能力

也就是：

- `项目是入口`
- `创作与输出是主流程`
- `场景、知识、技能是支撑层`
