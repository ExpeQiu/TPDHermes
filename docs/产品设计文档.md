**二、按该思路反推前后端改造清单**

下面我按“前端 / 后端 / 数据 / 流程 / 优先级”来拆。

---

**1. 前端改造清单**

**1.1 项目管理**
目标：
- 把项目页做成真正的业务主入口

需要改造：
- 项目详情页强化以下内容：
  - 项目描述
  - 项目附件
  - 历史输出
  - 执行记录
- 项目详情页只保留两个核心动作：
  - `进入对话创作`
  - `进入场景输出`
- 场景编排入口放弱，不再作为项目主流程动作
- 项目列表页增加状态筛选、最近输出概览

需要统一：
- 从项目进入 `/chat` 必须自动带上项目上下文
- 从项目进入 `/workshop` 必须自动带上项目上下文

---

**1.2 对话创作**
目标：
- 变成“基于项目的开放式生产入口”

需要改造：
- 聊天页默认从 `project_id` 启动
- 页面顶部展示当前项目边界
- 支持引用：
  - 项目描述
  - 项目附件摘要
  - 历史输出
- 支持将最终对话结果保存为 `Output`
- 支持“转为场景输出”或“基于当前结果继续优化”

应去掉或收敛：
- 过强的“手动拼上下文”心智
- 前端显式 prompt 组装感

---

**1.3 场景输出**
目标：
- 变成“标准化生产入口”

需要改造：
- 页面只允许从项目进入，或进入后必须先选项目
- 先选项目，再选场景
- 场景列表优先显示项目已启用的场景
- 页面展示内容改为：
  - 当前项目
  - 当前场景
  - 场景说明
  - 输出模板摘要
  - 关联技能摘要
- 本次输入区只保留：
  - 标题
  - 背景补充
  - 关键词
  - 目标
  - 额外要求
- 不允许在工坊里重新完整编排 skill 和模板策略

应新增：
- `结果优化` 入口必须真正带入已有 `output`
- 支持从某个历史输出进入“优化模式”

---

**1.4 场景编排**
目标：
- 变成规则设计中心，而不是生成入口

需要改造：
- 页面核心结构改为：
  - 场景说明
  - 关联 Skills
  - 定义输出模板
  - 定义输出规则
  - 保存合同
- 页面不再强调“即时生成内容”
- “预览”只预览合同，不直接当输出结果
- 场景编排页与项目页分离：
  - 全局维护场景
  - 项目只绑定场景，不在这里生产结果

---

**1.5 知识管理**
目标：
- 聚焦公共知识库管理

需要改造：
- 页面术语统一成“公共知识库”
- 支持：
  - 集合列表
  - 文档上传
  - 文档删除
  - 检索测试
  - 集合说明
- 不在这里处理项目级知识编排逻辑

---

**1.6 技能管理**
目标：
- 聚焦公共技能和个人技能

需要改造：
- 页面分区：
  - 公共技能库
  - 我的 Skills
- 支持：
  - 上传个人 Skill
  - 启用 / 禁用
  - 查看版本
  - 基础配置
- 工坊执行页不再承担技能管理职责

---

**2. 后端改造清单**

---

**2.1 项目相关接口**
目标：
- 项目成为主上下文中心

保留并增强：
- `GET /projects`
- `GET /projects/{id}`
- `PUT /projects/{id}`
- `GET /projects/{id}/outputs`
- `GET /projects/{id}/runs`
- `GET /projects/{id}/attachments`
- `POST /projects/{id}/attachments`

建议新增 / 强化：
- `GET /projects/{id}/summary`
  - 返回项目基础信息 + 最近输出 + 附件统计
- `GET /projects/{id}/context`
  - 返回供对话创作使用的项目上下文摘要

---

**2.2 对话创作执行接口**
目标：
- 对话创作正式项目化

建议保留：
- `POST /tasks/execute`，`entrypoint = chat`

建议增强：
- `chat` 模式下支持结构化输入：
  - `project_id`
  - `task_input`
  - `messages`
- 将项目附件摘要、历史输出摘要纳入编排服务
- 结果生成后允许回写 `outputs`

---

**2.3 场景输出执行接口**
目标：
- 工坊成为场景合同执行器

建议保留：
- `POST /tasks/execute`，`entrypoint = workshop`

建议增强：
- 入参必须显式包含：
  - `project_id`
  - `scenario_id`
  - `task_input`
- 后端强校验：
  - 项目存在
  - 场景存在
  - 项目是否允许使用该场景
- 场景合同必须由后端组装，不依赖前端本地预设

---

**2.4 场景编排接口**
目标：
- 支持场景合同完整管理

需要建设 / 完善：
- `POST /scenarios`
- `GET /scenarios`
- `GET /scenarios/{id}`
- `PUT /scenarios/{id}`
- `POST /scenarios/{id}/publish`
- `POST /scenarios/{id}/disable`
- `POST /scenarios/{id}/preview`

建议新增：
- `GET /scenarios/{id}/contract`
  - 返回场景合同摘要
- `GET /scenarios/{id}/usage`
  - 返回被哪些项目使用

---

**2.5 知识管理接口**
目标：
- 面向公共知识库

需要明确：
- `GET /kb/collections`
- `POST /kb/query`
- 公共知识文档上传接口
- 文档删除接口
- 集合元数据接口

建议新增：
- `POST /kb/collections`
- `DELETE /kb/collections/{name}`
- `POST /kb/collections/{name}/documents`

---

**2.6 技能管理接口**
目标：
- 支持公共技能和个人技能

保留：
- `/skills/*`
- `/ws/skills`

建议新增或区分：
- 公共技能列表
- 当前用户个人技能列表
- 上传个人 skill 接口
- 技能归属字段：`public / personal`

**4. 核心流程改造清单**

---

**4.1 项目 -> 对话创作**
需要保证：
- 项目页进入聊天时，项目上下文自动带入
- 聊天结果可保存为输出
- 可引用项目附件 / 历史输出
- 不要求必须选场景

---

**4.2 项目 -> 场景输出**
需要保证：
- 必须先有项目
- 必须选场景
- 场景必须有合同
- 生成结果后自动回写项目输出
- 可从历史输出发起优化

---

**4.3 场景编排 -> 场景合同**
需要保证：
- 场景编排保存的是规则
- 不直接变成输出正文
- 可发布版本
- 项目只绑定发布版本

---

**4.4 公共知识 / 技能供给**
需要保证：
- 对话创作和场景输出都调用同一套知识与技能供给体系
- 公共知识是统一资源
- 公共技能与个人技能是统一技能入口的两种归属类型

**5. 当前代码库的重点修复项**

结合你当前代码，优先要改的是这些：

**P0**
- 统一项目跳转参数
  - `/projects/[id] -> /chat`
  - `/projects/[id] -> /workshop`
- `chat` 页支持 `project_id`
- `create` 页明确不走项目执行，只做场景保存
- `workshop` 页改为优先读取项目绑定场景，而不是全局场景列表

**P1**
- `workshop` 增加真实的 `task_input`
- `refine` 模式支持带入 `output_id` 和旧内容
- 项目页支持按场景查看输出历史

**P2**
- 场景编排页去掉“即时生成结果”的暗示
- 技能管理区分公共技能和个人技能
- 知识管理统一到公共知识库概念

**P3**
- 对话创作支持从项目附件抽取摘要
- 输出结果支持审批 / 归档 / 导出
- 场景版本使用情况追踪

**7. 一句话结论**

按你这套思路反推，最重要的改造方向是：

- 让`项目`真正成为入口
- 让`场景`真正成为合同

- 让`知识管理 / 技能管理`回到支撑层
