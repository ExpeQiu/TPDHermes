## TPDHermes 完整产品介绍

**TPDHermes** 是一款面向技术推广与企业内容生产的 AI 共创平台，聚焦“从需求澄清到标准化交付”的全链路提效。  
产品以**项目（Project）**为组织核心，融合**对话式创作**与**场景化输出**两种工作模式，并通过 Agent + MCP 架构将知识库、技能模板、外部系统能力统一接入，实现可复用、可追溯、可扩展的内容生产体系。

---

## 1) 产品定位

TPDHermes 的定位是：**技术推广内容智能生产中台**。  
它解决的核心问题不是“单次生成一段文案”，而是“在真实业务环境下持续产出高质量内容”：

- 把分散的需求、资料、历史输出沉淀到项目上下文
- 把不同类型产出抽象为可编排的场景合同
- 把 AI 推理与工具调用交给统一 Agent 执行
- 把生成过程与结果纳入可管理、可复盘、可迭代的闭环

---

## 2) 目标用户

- 技术品牌与市场团队
- ToB/车企技术传播团队
- 方案、研究、演讲、活动内容制作人员
- 需要高频产出“技术类标准文档”的运营与咨询角色

---

## 3) 典型业务场景

- 技术趋势解读与行业洞察
- 发言稿/演讲稿生成与润色
- A4 一页纸方案提炼
- 视频脚本与传播素材生成
- 多项目并行下的内容复用与风格统一

---

## 4) 核心能力

- **项目中心化管理**：围绕项目统一管理描述、附件、历史输出与执行记录
- **对话创作模式**：支持多轮澄清、迭代共创，适合探索性需求
- **工坊场景输出模式**：按预定义场景模板一键生成，适合标准化交付
- **场景编排能力**：定义技能策略、知识策略、输出结构与校验规则
- **知识库能力**：文档 ingest、向量检索、事件同步与降级保障
- **技能体系（Skills）**：内置并可扩展行业技能，提升生成稳定性与专业度
- **任务化执行与追踪**：生成任务可提交、可观察、可回溯

---

## 5) 产品架构（简述）

TPDHermes 采用“**业务编排层 + Agent 执行层 + MCP 工具层**”三层架构：

- **TPDHermes（业务编排层）**  
  负责项目、场景、知识、技能、任务、结果持久化与 API 暴露

- **Hermes-agent（执行层）**  
  负责推理、工具选择、上下文融合与最终内容生成

- **MCP Server（能力接入层）**  
  将知识查询、项目操作、工坊生成等业务动作标准化为可发现工具，供 Agent 调用

该设计让“产品逻辑”和“推理执行”解耦，既便于业务快速迭代，也便于后续扩展新工具与新模型。

---

## 6) 技术栈与工程形态

- **前端**：Next.js（App Router）+ TypeScript + Tailwind
- **后端**：FastAPI + Pydantic + SQLAlchemy（异步）
- **数据层**：SQLite（可扩展其他数据库）+ Chroma（向量检索）
- **AI 协同**：Hermes-agent + MCP
- **部署形态**：本地脚本一键启动 + Docker Compose 多服务部署
- **运维脚本**：`start.sh` / `stop.sh` / `verify.sh` 覆盖启动、停止、验证闭环

---

## 7) 关键价值与差异化

- **从“对话工具”升级为“生产系统”**：强调项目资产沉淀和过程可治理
- **双引擎模式**：探索式对话与标准化场景并存，兼顾灵活性与稳定性
- **MCP 可扩展生态**：业务能力工具化，新增能力不必重写 Agent 内核
- **企业级可观测与可复盘**：任务、日志、结果可追踪，便于质量治理和问题定位
- **面向技术推广深度适配**：围绕真实交付物（趋势、发言、A4、脚本）构建能力

---

## 8) 当前成熟度与适用边界

- 已形成可用闭环：项目管理、对话生成、场景执行、知识与技能接入
- 部分模块处于持续演进：如技能市场产品化、反馈闭环与更完整评审链路
- 更适合“技术内容生产与复用”场景；对于强交易型、强实时协同型场景需按需扩展

---

## 9) 一句话总结

**TPDHermes 不是单点生成工具，而是将“项目上下文 + 场景合同 + Agent 执行 + 知识技能”打通的技术推广内容生产平台，帮助团队稳定、规模化地交付高质量内容。**


## TPDHermes 内部汇报版（架构与 ROI 导向）

### 1. 项目定位（管理层视角）

TPDHermes 定位为“**技术推广内容生产中台**”，目标不是替代单次写作，而是建立可复用、可度量、可持续优化的内容生产系统。  
核心业务价值：将“需求澄清 → 内容生成 → 质量校验 → 资产沉淀”标准化，降低人力波动与交付不确定性。

---

### 2. 当前业务痛点与建设目标

- **痛点 1：交付依赖个人经验**
  - 同类内容（趋势稿、演讲稿、A4 一页纸）重复劳动高，质量稳定性差。
- **痛点 2：知识资产分散**
  - 历史资料、项目上下文、团队经验缺乏结构化复用。
- **痛点 3：AI 使用碎片化**
  - Prompt 分散在前端和个人习惯中，难以治理、审计、复盘。
- **痛点 4：缺乏可观测性**
  - 问题排查依赖人工还原，缺少统一执行日志与调用链证据。

**建设目标（12 个月）**：
1) 建立统一编排与执行架构；  
2) 把高频内容场景模板化；  
3) 建立全链路日志与成本看板；  
4) 将内容生产效率提升 30%+，返工率降低 20%+。

---

### 3. 系统架构总览（分层解耦）

#### 3.1 架构分层

- **业务编排层（TPDHermes）**
  - 管理项目、场景、知识、技能、任务、结果落库；
  - 提供统一 API（`/api/v1`）与业务边界控制。
- **智能执行层（Hermes-agent）**
  - 负责推理、工具选择、上下文融合、内容生成。
- **能力接入层（MCP）**
  - 将知识查询、项目操作、工坊生成等动作标准化为工具接口。

#### 3.2 架构价值

- 业务逻辑与 AI 推理解耦，降低后续模型切换/能力扩展成本；
- 通过 MCP 工具化集成外部能力，减少“改一处牵全局”的风险；
- 对话模式与场景模式并存，兼顾探索效率与标准化交付。

---

### 4. 核心能力与业务映射

- **项目中心化**：每个任务绑定项目上下文，保障内容一致性与可追溯。
- **对话创作**：用于需求澄清、方向探索、专家共创。
- **工坊场景输出**：用于标准件高频交付（趋势、发言、A4、脚本）。
- **知识库能力**：资料 ingest + 检索 + 事件同步，支撑事实一致性。
- **技能体系（Skill）**：沉淀行业最佳实践，降低“临场 Prompt 工程”成本。
- **任务化执行**：执行状态、结果、失败原因可追踪，便于运营治理。

---

### 5. ROI 评估模型（建议采用）

> 说明：以下为内部可落地的 ROI 口径，数值可按你们实际人力单价与产量替换。

#### 5.1 直接收益（效率）

**公式**：  
`年度节省人力成本 = 年内容产量 × 单篇节省工时 × 人工小时成本`

示例（可替换参数）：
- 年产量：2,400 篇（200/月）
- 单篇节省：1.5 小时
- 小时成本：220 元

则：`2,400 × 1.5 × 220 = 792,000 元/年`

#### 5.2 质量收益（返工率）

**公式**：  
`返工节省 = 年产量 × 返工率下降 × 单次返工工时 × 小时成本`

示例：
- 返工率下降：12%
- 单次返工：1 小时

则：`2,400 × 12% × 1 × 220 = 63,360 元/年`

#### 5.3 管理收益（交付可预测性）

- 计划准确率提升（排期偏差下降）
- 人员替换风险下降（经验沉淀到系统）
- 培训周期缩短（新人基于场景模板快速上手）

> 管理收益建议以 KPI 呈现，不强行货币化，以免失真。

#### 5.4 投入项（TCO）

- 人力投入：前后端、算法/Agent、产品运营
- 资源投入：模型调用、向量库、容器资源
- 运维投入：监控告警、日志存储、发布与回滚机制

#### 5.5 ROI 汇总口径

`ROI = (效率收益 + 质量收益 + 其他可量化收益 - 年化总投入) / 年化总投入`

---

### 6. 可观测性与治理（重点）

为满足“过程可排查、结果可复盘”，建议固化以下能力：

- **执行日志标准化**：任务 ID、项目 ID、场景 ID、模型、Token、耗时、工具调用链、错误码。
- **调用链追踪**：前端请求 → 后端编排 → Agent 调用 → MCP 工具 → 结果落库。
- **质量指标看板**：
  - 首次通过率、人工修改率、返工率、平均交付时长。
- **成本指标看板**：
  - 单任务 Token 成本、单项目月成本、场景成本排名。
- **故障排查清单**（建议固定 SOP）：
  - 环境变量 → 网络 → 外部服务余额/配额 → 日志 → Mock 回退。

---

### 7. 分阶段推进建议（内部实施）

- **阶段 A（1-2 个月）稳定主链路**
  - 打通项目-场景-任务闭环；统一日志字段；建立最小看板。
- **阶段 B（2-4 个月）扩展高频场景**
  - 上线 3-5 个核心场景模板；建立技能版本管理与回滚策略。
- **阶段 C（4-6 个月）经营化运营**
  - 建立 ROI 月报机制；按场景做 A/B 优化；推进知识收割闭环。

---

### 8. 关键风险与对策

- **风险：模型成本不可控**  
  对策：按场景设置模型等级、Token 上限、超限降级策略。
- **风险：输出质量波动**  
  对策：引入结构化输出合同 + 自动校验 + 人审抽检。
- **风险：外部依赖故障（向量库/三方接口）**  
  对策：Mock/缓存降级 + 健康检查 + 自动告警。
- **风险：模板僵化影响创新**  
  对策：保留“对话探索”通道，与“场景标准化”并行。

---

### 9. 对管理层的结论

TPDHermes 的战略价值不在于“多快写一篇”，而在于建立**可规模化复制的内容生产能力**。  
从架构上看，分层解耦和 MCP 工具化保障了中长期扩展性；从经营上看，效率与返工率两项已具备清晰 ROI 口径。  
建议继续投入，但聚焦三件事：**主链路稳定、数据可观测、场景经营化**，确保平台从“可用”走向“可经营”。
