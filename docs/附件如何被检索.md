我先把“项目附件 -> 抽取/入库 -> 项目级知识库 -> 编排注入 -> LLM 检索调用”这条链路补齐，重点确认附件是怎么进 `project.{id}.kb`，以及编排时怎么把这个 collection 暴露给模型。
        
链路已经齐了。结论先说：**项目附件不是把原文件全文直接塞进 prompt 给 LLM，而是先异步抽取成 Markdown，写进项目级知识库 `project.{project_id}.kb`，再由 Agent 通过 `kb_query` / `kb_get_entry` 这类 MCP 工具按需检索调用。****核心结论**
- 项目附件里的信息，被 LLM 调用的方式是：`上传附件 -> 异步抽取文本 -> 写入项目级知识库 -> 编排把项目 KB collection 注入给 Agent -> Agent 通过 MCP 的 KB 工具检索到附件片段`。
- 也就是说，**附件内容默认不会整篇直接进模型上下文**，而是走 RAG/KB 检索链路，按需召回。

**实现链路**
- 附件上传后，后端会把二进制文件存到项目上传目录，并在 `project_attachments` 表里记录元数据；随后立刻触发异步索引任务 `schedule_ingest_attachment()`。[projects.py](file:///Volumes/Lexar/git/03T/TPDHermes/backend/routes/projects.py#L651-L708) [project_attachment.py](file:///Volumes/Lexar/git/03T/TPDHermes/backend/models/project_attachment.py#L11-L26)
- 异步任务 `ingest_project_attachment()` 会读取附件记录，定位磁盘文件，然后调用 `extract_to_markdown()` 把附件转成可索引文本。[project_kb_ingest.py](file:///Volumes/Lexar/git/03T/TPDHermes/backend/services/project_kb_ingest.py#L236-L285) [document_extract.py](file:///Volumes/Lexar/git/03T/TPDHermes/backend/services/document_extract.py#L23-L43)
- 当前支持的抽取格式包括：
  - 纯文本类：`.txt`、`.md`、`.markdown`、`.csv`、`.json`
  - `.pdf`
  - `.docx`
  - 不支持的格式会直接失败，附件不会进入 KB。[document_extract.py](file:///Volumes/Lexar/git/03T/TPDHermes/backend/services/document_extract.py#L10-L18) [document_extract.py](file:///Volumes/Lexar/git/03T/TPDHermes/backend/services/document_extract.py#L31-L43)
- 抽取后的文本会以 `source_type="project_attachment"`、`folder_path="attachments"`、`published=True` 的方式走统一 KB 入库逻辑，目标 collection 是 `project.{project_id}.kb`。[project_kb_ingest.py](file:///Volumes/Lexar/git/03T/TPDHermes/backend/services/project_kb_ingest.py#L259-L270) [project_kb.py](file:///Volumes/Lexar/git/03T/TPDHermes/backend/services/project_kb.py#L25-L29)

**怎么进知识库**
- 附件不会走一条特殊旁路，而是复用统一的 ingestion：先构造 manifest，再调用 `run_kb_ingestion()`。[project_kb_ingest.py](file:///Volumes/Lexar/git/03T/TPDHermes/backend/services/project_kb_ingest.py#L101-L144)
- 统一 ingestion 会做这些事：
  - 读取正文
  - 切 chunk
  - 生成 `doc_id` / `chunk_id`
  - 补 metadata
  - 可选 embedding
  - upsert 到 Chroma
  - 清理旧 chunk
- 这部分主逻辑在 `run_kb_ingestion()` 里。[kb_ingest_core.py](file:///Volumes/Lexar/git/03T/TPDHermes/backend/services/kb_ingest_core.py#L154-L396)
- 附件索引成功后，还会执行两件关键事：
  - 回写附件表字段：`ingest_status`、`kb_doc_id`、`chunk_count`
  - 把项目级 collection 写进项目配置，确保后续编排默认带上它。[project_kb_ingest.py](file:///Volumes/Lexar/git/03T/TPDHermes/backend/services/project_kb_ingest.py#L272-L285) [project_kb.py](file:///Volumes/Lexar/git/03T/TPDHermes/backend/services/project_kb.py#L68-L103)

**怎么暴露给 LLM**
- 编排组装时，`assemble_payload()` 会把项目默认知识集合和 `project.{project_id}.kb` 合并，写进 `payload.knowledge.collections`。[orchestration_service.py](file:///Volumes/Lexar/git/03T/TPDHermes/backend/services/orchestration_service.py#L530-L548)
- 这意味着只要带了 `project_id`，模型执行时就天然知道这个项目自己的 KB collection 在可检索范围内。
- 测试也明确覆盖了这点：编排预览结果里必须包含 `project_kb_collection(pid)`。[test_project_kb_ingest.py](file:///Volumes/Lexar/git/03T/TPDHermes/tests/test_project_kb_ingest.py#L83-L94)

**LLM 实际调用什么**
- Agent 不是直接查数据库，而是通过 MCP Server 暴露出来的 KB 工具调用附件内容：
  - `kb_query`
  - `kb_get_entry`
- 这些工具在 `backend/mcp_server.py` 里注册，并且在 agent 配置里被显式放进 `include` 白名单。[mcp_server.py](file:///Volumes/Lexar/git/03T/TPDHermes/backend/mcp_server.py#L29-L70) [config.yaml](file:///Volumes/Lexar/git/03T/TPDHermes/deploy/hermes-agent/config.yaml#L6-L31)
- `kb_query()` 最终会调用 `kb_proxy_service.query_collection()`，对指定 collection 做语义检索；如果上游不可用，再回退到本地 `kb_cache`。[kb_tools.py](file:///Volumes/Lexar/git/03T/TPDHermes/backend/tools/kb_tools.py#L66-L88) [kb_tools.py](file:///Volumes/Lexar/git/03T/TPDHermes/backend/tools/kb_tools.py#L231-L303)

**为什么 LLM 能查到“附件”而不是别的文档**
- 附件被入库时，固定写到项目专属 collection：`project.{project_id}.kb`。[project_kb.py](file:///Volumes/Lexar/git/03T/TPDHermes/backend/services/project_kb.py#L25-L29)
- 附件 metadata 里带了：
  - `source_type="project_attachment"`
  - `source_id=附件 id`
  - `project_id`
  - `folder_path="attachments"`
- 所以它既能被项目维度隔离，也能被后续浏览和治理区分出来。[project_kb_ingest.py](file:///Volumes/Lexar/git/03T/TPDHermes/backend/services/project_kb_ingest.py#L69-L131)

**调用时的几个前提**
- 附件必须已经索引成功，也就是 `ingest_status = "ingested"`；否则它只是上传了文件，还没变成可检索知识。[projects.py](file:///Volumes/Lexar/git/03T/TPDHermes/backend/routes/projects.py#L620-L648)
- 附件格式必须可抽取；比如二进制未知格式会失败，不会进入 KB。[document_extract.py](file:///Volumes/Lexar/git/03T/TPDHermes/backend/services/document_extract.py#L43-L43)
- 调用时必须带项目上下文，才能把对应的 `project.{project_id}.kb` 注入编排 payload。[orchestration_service.py](file:///Volumes/Lexar/git/03T/TPDHermes/backend/services/orchestration_service.py#L530-L548)

**一句话版**
- 项目附件信息之所以能被 LLM 调用，是因为它先被异步“文本化 + 切块 + 向量化”写进项目专属 KB，然后在模型执行时通过 `kb_query` 这类 MCP 工具按需检索出来，而不是直接把附件原文塞给模型。
