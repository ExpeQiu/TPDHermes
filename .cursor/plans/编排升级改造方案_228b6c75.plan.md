# 编排升级改造方案（对齐文档）

## 核心结论

方案本质不是「给 Agent 更多上下文」，而是 **TPDHermes 发布结构化任务合同（`OrchestrationPayload`），Hermes-agent 按合同执行**；TPDHermes 管边界与规则，Agent 管推理、检索、工具与成稿。

```mermaid
flowchart LR
  subgraph ui [前端多入口]
    Chat[/chat]
    Create[/create]
    Workshop[/workshop]
    Proj[/projects]
  end
  subgraph tp [TPDHermes]
    OrchSvc[orchestration_service]
    AgentGw[agent_gateway]
    Persist[outputs_runs]
  end
  subgraph ha [Hermes-agent]
    Exec[MCP与推理]
  end
  ui -->|结构化任务请求| OrchSvc
  OrchSvc --> AgentGw
  AgentGw -->|编排+消息| ha
  ha --> Exec
  Exec -->|正文与metadata| Persist
```

## 编排合同：`OrchestrationPayload`

与 Agent 之间的正式协议，字段含义（文档第五节、第六节）：

| 块 | 职责 |
|----|------|
| `project` | 项目背景、受众、长期约束 |
| `scenario` | 场景意图、协作模式 |
| `domain` | 技术/业务边界、术语策略 |
| `knowledge` | 集合、是否项目绑定、top_k、降级策略 |
| `skills` | 白名单/偏好/是否允许 Agent 自选 |
| `output` | 模板 ID、格式、章节、校验规则 |
| `execution` | 流式、trace、落库策略 |
| `user_input` | 本次自然语言输入，与编排分离 |

Agent 侧建议用 `extra.orchestration` 传递；短期可退化为 system 内严格 JSON 块（文档第十二节）。

## 职责边界（ recap ）

- **TPDHermes**：项目/场景/模板/知识策略、任务提交、结果与评审持久化。
- **Hermes-agent**：理解任务、选工具、检索、技能组合、遵循模板、多轮生成。
- **MCP**：继续暴露 `projects`、`kb`、`workshop` 等（[backend/mcp_server.py](backend/mcp_server.py)）。
- **前端**：收集输入、编排预览、发起执行、展示历史；**不再**拼装长提示词（当前痛点见 [src/lib/chat-context.ts](src/lib/chat-context.ts)、[src/app/chat/page.tsx](src/app/chat/page.tsx)）。

## 后端与数据（文档第十三至十七节）

**建议新增/强化模块**

- `backend/services/orchestration_service.py`：组装 `OrchestrationPayload`
- `backend/services/agent_gateway.py`：适配 Hermes-agent 请求格式
- `backend/services/template_service.py`、`run_log_service.py`
- 路由：`POST /api/v1/tasks/execute`、`/projects/{id}/orchestration/preview` 等；或将 [backend/routes/chat.py](backend/routes/chat.py) 升级为编排任务入口（保留兼容层，文档第二十节）

**数据模型方向**

- 启用并映射 [schema.sql](schema.sql) 中 `templates`、`outputs`
- 新增：`project_configs`、`orchestration_runs`；扩展 `projects` 外键到 `domain_profile`、`knowledge_policy`、`default_template` 等；可选 `domain_profiles`、`knowledge_policies`、`scenario_profiles`（文档第十五节）

## 前端改造方向（文档第十四节）

| 页面 | 目标 |
|------|------|
| `/create` | 快捷场景编排页，非静态跳转器 |
| `/chat` | 编排协作页，展示边界/策略/执行摘要，去掉前端拼的 MCP 上下文展示 |
| `/workshop` | 统一走编排任务；`/ws/generate` 逐步内化为 Agent/编排调用 |
| `/projects/[id]` | 控制台：技术域、知识域、模板、输出物、运行记录 |
| `/knowledge` | 浏览 +「加入项目知识范围」 |

## 分阶段实施（文档第二十一、二十二节）

文档明确 **第一步优先后端协议与落库，而非先大改 UI**。

1. **P0**：`OrchestrationPayload` + `orchestration_service` + `POST .../tasks/execute` + 模板/输出物表与 ORM 映射。
2. **P1**：`/chat` 改走编排执行（UI 可渐进）；项目详情接真实 `outputs` / `runs`。
3. **P2**：`/create`、`/workshop` 并入同一任务接口；模板校验、引用、技能白名单。
4. **P3**：专用/公共知识与技能分层、审批与审计。

## 风险与验收（摘要）

- **风险**：Agent 暂不支持 `extra.orchestration` → 后端 prompt 适配过渡；技能输出形态不一 → 统一 Skill 输出协议逐步收敛；双轨前端 → **先统一后端任务接口再切页**（文档第二十三节）。
- **验收**（文档第二十四节）：多入口同一 `tasks/execute`、项目可配域/知识/默认模板、结果写入 `output` 并关联 `run`、编排与用户输入可区分、模板基础校验有用户可见反馈。

## 与现有代码的衔接（文档第二十节）

保留 [backend/routes/chat.py](backend/routes/chat.py) 中 `chat/config` 与代理作为兼容层；保留 MCP；`chat-context.ts` 降级为编排预览；`workshop` 直连 skill 逐步收敛为编排入口。
